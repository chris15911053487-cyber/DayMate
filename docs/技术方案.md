## 0. 已确定的前提

| 事项 | 结论 |
|---|---|
| 首发形态 | H5 网页（PWA），手机和电脑浏览器都能用；后期扩展 iOS/安卓 App 和微信小程序 |

## 1. 范围与分期

### 1.1 需求对照

| 原始需求 | 方案 | 阶段 |
|---|---|---|
| 未来计划，以语音录入为主 | 按住说话 → AI 拆成日程/待办 → 确认卡片 → 保存 | P1 |
| 记录当天发生的事 | "记录"模块：语音或文字，按天排成时间流，可挂到某条日程下 | P1 |
| AI 判断、总结、建议 | 一句话解析、冲突提示、早报、晚间复盘、语音问日程 | P1 |
| 推送信息 | 站内消息 + Web Push + 邮件；App 和小程序推送随对应端上线 | P1 / P3 |
| 主题风格可选、可 DIY | 预设主题 + 自定义主色、背景、字体、圆角等 | P1（主题分享 P2） |
| 知识库管理 | 笔记、语义检索、基于个人数据问答 | P2 |
| 团队协作沟通 | 团队空间、共享日历、邀请、评论 | P3 |
| 分享到微信 | 分享为图片或链接（P2）；自定义分享卡片需要公众号（P3） | P2 / P3 |
| App、小程序 | App 用 Capacitor 打包现有网页；小程序用 Taro 另写界面，复用后端和共享代码 | P3 |

### 1.2 P1（MVP）范围

**做：**

- 账号：注册、登录（用户名或邮箱）、邮箱验证、找回密码、修改密码、登录设备管理、注销账号
- 语音：按住说话（从 online-report 移植），文字输入兜底；一句话可拆出多条日程、待办或记录；能语音提问"明天有什么安排"
- 日历：日历本（工作、生活等）、日程、待办，月/周/日视图，"今天"首页，简单重复（每天、工作日、每周、每月、每年），关键词搜索
- 记录：当天记录的增删改查，按天浏览
- AI：一句话解析、冲突提示、早报、晚间复盘
- 推送：站内消息、Web Push、邮件，提醒设置，免打扰
- 个性化：12 套预设主题 + DIY
- 部署：docker compose 一键部署，包含 HTTPS 和数据库备份

**暂不做：**

- 语音修改、删除已有日程（P1 在界面上改）
- 超过 60 秒的连续语音转写（P1 分段续录）
- 离线编辑（P1 离线时只有页面外壳）
- 重复日程"只改这一次"
- 知识库、团队协作、微信分享、App、小程序
- 手机号登录、微信登录、图形验证码
- 管理后台页面（P1 用命令行脚本处理封禁账号等运维操作）
- 数据自助导出（P1 有需要时人工导出）

### 1.3 P2 / P3 概览

**P2**：语音改/删日程；重复日程单次修改；实时流式语音识别（长语音、边说边出字）；知识库（笔记、AI 自动打标签、pgvector 语义检索、"问我自己的记录"）；周报和月报；数据导出（JSON、ICS）；分享为图片；主题分享码；图形验证码；手机号登录；简单管理后台。

**P3**：团队协作（团队空间、成员角色、共享日历、日程邀请与回复、评论和 @、团队周报）；App（Capacitor 打包，接厂商推送通道和本地通知）；微信小程序（Taro；录音可直接录 16k WAV，复用同一个识别接口；提醒走订阅消息）；微信登录；公众号消息推送；微信 JSSDK 自定义分享卡片。

**P1 就预留的扩展点：**

- 日程挂在"日历本"上，P3 给日历本加成员就能共享。
- 推送走统一出口，以后加渠道只需加一个发送器。
- 接口用 Bearer 令牌，App 和小程序可以直接调用。
- 校验规则和类型放在共享包里，小程序可以复用。

## 2. 总体架构

```
手机 / 电脑浏览器（PWA）
   │  HTTPS
   ▼
Caddy ── 反向代理，自动申请、续期 HTTPS 证书
   │
   ▼
app（Node.js + Fastify，一个容器）
   ├─ 网页静态文件（React 构建产物）
   ├─ REST 接口 /api/*
   ├─ 语音识别代理 ──→ 百度短语音识别
   ├─ AI 助手 ──────→ 大模型（OpenAI 兼容接口）
   ├─ 后台任务：提醒扫描、早报、晚间复盘
   └─ 推送：站内消息 / Web Push / 邮件（SMTP）
   │
   ▼
PostgreSQL ── 数据卷持久化；镜像自带 pgvector，给知识库预留
```

- 前后端在同一个容器、同一个域名下，没有跨域问题（同 online-report）。
- 不像 online-report 那样单独起一个 Python AI 服务。DayMate 的 AI 主要做结构化解析和总结，Node 里直接调模型接口就够了，少一个服务就少一份运维。以后需要复杂 Agent 时再拆出去。
- 后台任务跑在 app 进程里。提醒扫描用数据库行锁（`FOR UPDATE SKIP LOCKED`），以后扩成多个实例也不会重复发送。

## 3. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 前端框架 | React 19 + Vite + TypeScript | 与 online-report 一致，语音、主题代码可以直接搬 |
| 样式 | Tailwind CSS 4 + CSS 变量主题 token | 沿用 online-report"只用语义色"的做法，换主题只换变量 |
| 路由 / 数据 / 状态 | React Router、TanStack Query、Zustand | 服务器数据交给 Query 缓存，界面状态用 Zustand |
| 日期 | 自写的时区与重复规则工具（`packages/shared/src/time.ts`、`recurrence.ts`，基于 Intl） | 前后端共用、无第三方依赖；支持夏令时；重复规则存 RRULE（行业标准） |
| PWA | vite-plugin-pwa | 生成 manifest 和 Service Worker，负责推送和"添加到主屏幕" |
| 后端 | Node.js 22 LTS + Fastify 5 + TypeScript | 复用 online-report 的 Fastify 经验；TS 可与前端、小程序共享类型 |
| 校验 | zod（放在共享包） | 前端表单、后端接口、AI 输出用同一套规则 |
| 数据库 | PostgreSQL 17 | 免费、适合 Docker；有带时区的时间类型、JSON、数组；pgvector 做语义检索 |
| ORM / 迁移 | Drizzle ORM + drizzle-kit | 写法接近 SQL、类型安全；迁移文件提交到仓库，启动时自动执行 |
| 密码哈希 | Argon2id（@node-rs/argon2） | 当前推荐的密码哈希算法；有预编译包，镜像里不用编译 |
| 语音识别 | 百度短语音识别（移植 online-report） | 已在生产环境验证；后端做成可替换的接口 |
| 大模型 | OpenAI 兼容接口（DeepSeek、通义千问等） | 一个客户端切换多家；面向国内公众要用已备案的模型 |
| 推送 | web-push（VAPID）、nodemailer（SMTP） | 标准方案，不需要第三方推送 SDK |
| 部署 | Docker Compose：app + PostgreSQL + Caddy | 一条命令起服务，Caddy 自动 HTTPS |
| 测试 | Vitest、Playwright | 单元测试和端到端测试 |

## 5. 账号体系

### 5.1 规则

- 注册时 **用户名、邮箱、密码** 三项必填；登录时 **用户名或邮箱任选一个 + 密码**。输入里带 `@` 就按邮箱查，否则按用户名查。
- 邮箱必填，是因为忘记密码要靠它找回，它也是提醒的兜底渠道。想降低注册门槛可以改成选填，代价是没填邮箱的用户忘了密码无法自助找回。
- 用户名 4–20 位，字母开头，可含字母、数字、下划线；不区分大小写，唯一。邮箱统一转小写后唯一。
- 密码 8–64 位，不能和用户名或邮箱相同，拦截常见弱密码（内置一份常见密码清单）。
- 注册后发验证邮件。没验证也能正常使用，页面顶部会提示去验证；邮件提醒要求邮箱已验证。
- 找回密码对未验证的邮箱也可用：能收到重置邮件本身就证明邮箱是他的，重置成功后顺带标记为已验证。

### 5.2 密码与登录保护

- 密码用 Argon2id 哈希存储，参数取 OWASP 推荐值（内存 19 MiB、迭代 2 次、并行度 1）。明文不落库，也不进日志。
- 登录失败一律提示"账号或密码错误"，不暴露账号是否存在。
- 限流：同一 IP 每分钟最多 10 次登录、每小时最多 5 次注册；同一账号连续输错 5 次后要等 15 分钟（P2 改成图形验证码）。
- "忘记密码"不管邮箱是否注册过都返回同样的提示，防止被用来探测账号。

### 5.3 会话与令牌

| 令牌 | 有效期 | 存放位置 |
|---|---|---|
| 访问令牌（JWT） | 30 分钟 | 前端内存；请求头 `Authorization: Bearer …` |
| 刷新令牌（随机串） | 30 天，每次刷新都换新 | H5：`HttpOnly`、`Secure`、`SameSite=Strict` 的 Cookie，路径限定 `/api/auth`；App/小程序：系统安全存储 |

- 数据库只存刷新令牌的哈希（`user_sessions` 表），一台设备一行，所以能做"登录设备列表"和"踢掉某台设备"。
- 刷新令牌每用一次就换新。如果已经换掉的旧令牌又被拿来用，说明可能泄露，立即作废这个会话。
- 修改密码时作废其他设备的会话；重置密码时作废全部会话。
- 访问令牌不放 localStorage（online-report 是放在 localStorage 的），降低被 XSS 窃取的风险。

### 5.4 邮件

- 验证邮件的链接 24 小时有效；重置密码的链接 30 分钟有效、只能用一次。令牌只存哈希。
- 用 nodemailer 通过 SMTP 发信。正式环境用阿里云邮件推送、腾讯云 SES 这类正规服务，并给域名配好 SPF/DKIM，否则邮件容易进垃圾箱。
- 开发环境用 Mailpit 容器收下所有邮件，在网页里查看，不会真的发出去。

接口见第 12 节。

## 6. 语音输入（复用 online-report）

### 6.1 链路

```
按住按钮 → 浏览器录音（开降噪、回声消除、自动增益）
        → 松开后多录 300ms；降采样到 16k 单声道；裁掉首尾静音；编码成 WAV
        → POST /api/speech/recognize（需登录，计入每日额度）
        → 后端调百度短语音识别 → 返回文字和 voiceLogId
        → 前端显示"我听到的"，同时交给 AI 解析（第 7 节）
```

### 6.2 从 online-report 移植的文件

| online-report 文件 | 放到 DayMate | 改动 |
|---|---|---|
| `frontend/src/utils/voiceRecorder.ts` | `apps/web/src/voice/recorder.ts` | 基本原样；接口调用改用新的 API 层 |
| `frontend/src/utils/voiceRecorder.test.ts` | 同目录 | 原样 |
| `frontend/src/hooks/useHoldToTalk.tsx` | `apps/web/src/voice/useHoldToTalk.tsx` | 换成 DayMate 的提示组件和样式；浮层位置配合底部中间的大按钮 |
| `server/src/baidu-asr.js` | `apps/server/src/asr/baidu.ts` | 改写成 TS；`cuid` 改成 `daymate-<用户ID>`；实现统一的识别接口 |
| `server/src/routes/speech.js` | `apps/server/src/modules/speech/` | 去掉调试接口；加额度检查；保留 4MB 的请求体上限 |
| `server/src/voice-logs.js` | 同上 | SQL Server 改成 PostgreSQL；按用户 ID 存 |

不移植的：

- `frontend/public/js/voice.js`：它是关键词指令、模拟点击页面。DayMate 的语音不是用来操作界面的。
- `mobile-webview/`：App 阶段改用 Capacitor（见 1.3）。

保留下来的好做法：

- 麦克风真正出数据后才提示"请说话"，避免吞掉第一个字。
- 上滑取消；最后 5 秒倒计时；按住不到 0.5 秒算误触。
- 不保存录音，只存识别出的文字。
- 纠错闭环：`voice_logs` 同时记识别结果和用户最终保存的文字，两者不同就是一条识别错误样本。样本可以导出给百度自训练平台，提高人名、地名的识别率（沿用 online-report `server/scripts/export-asr-corpus.js` 的思路）。

### 6.3 交互

- 手机底部导航中间是一个大的"按住说话"按钮，在任何页面都能直接说。电脑上按住麦克风按钮说话（同 online-report）。
- 松开后弹出底部面板：上面是"我听到的"（可以改），先显示出来；下面是 AI 解析出的卡片，解析时先显示占位。每张卡片显示类型、标题、时间、地点、提醒、冲突提示，以及 AI 拿不准的地方。
- 操作：全部保存 / 单条编辑 / 丢弃。设置里可以打开"说完直接保存"，保存后 5 秒内可撤销。
- 记日记这类长内容：一次最长 60 秒，到时自动结束并识别；再按住继续说，文字接在后面。
- 面板里随时可以改用键盘输入，走同一套 AI 解析。轻点语音按钮（不按住）就是打字；没有麦克风权限或不是 HTTPS 时也自动改成打字。

### 6.4 限制与对策

| 问题 | 对策 |
|---|---|
| 浏览器只在 HTTPS 下允许用麦克风 | 部署用 Caddy 自动 HTTPS；开发时 `localhost` 可用，手机真机调试要用 mkcert 或 Caddy 的本地证书 |
| 百度短语音一次最长 60 秒 | P1 分段续录；P2 换成百度实时语音识别（WebSocket 流式） |
| 部分浏览器不能按 16k 采样率录音 | 录音代码里已经有降采样兜底 |
| 微信内置浏览器 | 一般能录音，需真机测试；但不能安装 PWA、收不到 Web Push，要引导用户"在浏览器打开" |
| 录音用的 `ScriptProcessorNode` 已被标为废弃 | 目前各浏览器仍支持；以后换成 AudioWorklet |
| 人名、地名识别不准 | 确认卡片可以改；积累纠错样本做自训练 |
| 公开用户刷接口产生费用 | 每人按分钟、按天限次（默认每天 100 次，可配置） |

## 7. AI 助手

### 7.1 能力清单（P1）

| 能力 | 什么时候触发 | 说明 |
|---|---|---|
| 一句话解析 | 用户说完或输入完 | 拆出日程、待办、记录，或者判断出这是一个提问 |
| 问日程 | "明天有什么安排""周五下午有空吗" | 先解析出时间范围，查库，再让 AI 只根据查到的数据回答，不许编造 |
| 冲突提示 | 保存前 | 规则判断时间是否重叠，不调 AI |
| 早报 | 每天早上（默认 7:30） | 今天的日程和待办、昨天没完成的事、冲突和"排得太满"的提醒，加一两条建议 |
| 晚间复盘 | 每天晚上（默认 21:30） | 根据今天的日程、待办完成情况和记录写总结和明天的建议；当天没有记录时提醒用户说两句 |

### 7.2 一句话解析

- AI 只输出"墙上时间"（日期 + 几点几分），不让它换算时区和时间戳，换算由服务端按用户时区完成。
- 用户消息里带上当前时间、星期、时区，以及未来 14 天的日期和星期对照表。有了对照表，"下周三""这周五"这类说法的准确率会明显提高。
- 一句话可以产出多条结果。
- 没说结束时间就用默认时长（可在设置里改，默认 1 小时）；没说提醒就用默认提醒（默认提前 15 分钟）。
- 重复日程由 AI 输出简化的结构（如 `{"freq": "weekly", "by_weekday": ["MO"]}`），服务端转成 RRULE。
- AI 拿不准的地方写进 `assumptions`，在卡片上标出来。

示例（今天是 2026-11-24，周二）：

> 明天下午三点和老王在国贸开会，提前半小时提醒我，还有这周五前把季度报告交了

```json
{
  "items": [
    {
      "type": "event",
      "title": "和老王开会",
      "date": "2026-11-25",
      "start_time": "15:00",
      "end_time": null,
      "all_day": false,
      "location": "国贸",
      "people": ["老王"],
      "remind_before_min": [30],
      "repeat": null
    },
    {
      "type": "task",
      "title": "交季度报告",
      "due_date": "2026-11-27"
    }
  ],
  "assumptions": ["没说结束时间，按默认 1 小时安排"],
  "reply": "好的：明天 15:00 在国贸和老王开会，14:30 提醒你；周五前交季度报告。"
}
```

`type` 的取值有 `event`（日程）、`task`（待办）、`entry`（记录）、`query`（提问）。P2 再加 `update`、`cancel`，用于语音改/删日程。完整结构用 zod 定义在 `packages/shared`。

### 7.3 提示词组织与成本

- 沿用 online-report 的前缀缓存约定：系统提示词（规则、输出格式、示例）固定不变，放在最前面；当前时间、用户信息、14 天对照表这些每次都变的内容放在用户消息里。这样模型厂商的上下文缓存能命中，既省钱又更快。
- 解析和总结可以配置成不同的模型：解析要快、要便宜，总结可以用效果更好的模型。
- 每次调用都记入 `ai_calls`（模型、token 数、耗时、是否成功），用来看成本和排查问题。
- 额度：每人每天的 AI 调用次数有上限（默认 100，可配置）。早报和复盘每人每天最多 2 次；7 天没打开过应用的用户不生成。

### 7.4 失败兜底

- AI 输出用 zod 校验，不合格就把错误信息交回模型重试一次。
- 仍然失败或模型超时：把原话存成一条"记录"草稿，提示用户手动整理。**用户说的话不能丢。**
- 模型服务整体不可用时，日历和记录的手动操作照常能用。

### 7.5 模型接入与合规

- 只依赖 OpenAI 兼容接口。`AI_BASE_URL`、`AI_API_KEY`、`AI_MODEL_PARSE`、`AI_MODEL_SUMMARY` 四个环境变量就能切换厂商。
- 在国内面向公众提供生成式 AI 功能，要按《生成式人工智能服务管理暂行办法》履行备案或登记手续。建议选用已备案的国内模型，具体流程以属地网信部门的要求为准。
- 选择承诺"不用接口数据训练模型"的厂商，并写进隐私政策。

### 7.6 评测集

`apps/server/eval/cases.json` 里放真实说法和期望结果（M3 先做了 40 条，逐步扩到 100 条），覆盖相对日期、一句话多件事、重复日程、模糊时间（"下午""晚上"）、口语和识别错字。改提示词或换模型前先跑一遍，按字段统计准确率。建议先定目标：日期和时间准确率 ≥ 95%，整体 ≥ 90%。

M3 实测（`deepseek-v4-flash`，`cd apps/server && npm run eval`）：首轮 38/40；补了一条规则（重复事项一律是日程）后连续两轮 40/40，平均每句约 1.5 秒。

## 8. 日历、待办与记录

### 8.1 概念

| 概念 | 说明 |
|---|---|
| 日历本 | 每个用户默认有一个"我的日历"，可以再建"工作""生活"等，各有颜色；P3 加成员就能共享 |
| 日程 | 有具体时间（或全天）的安排，属于某个日历本 |
| 待办 | 要做的事，可以有截止日期，也可以没有；可以勾选完成。只有截止日期、没有具体时间的待办在当天早报里提醒 |
| 记录 | 当天发生的事，按天组织；可以挂在某条日程下（比如"会开完了，结论是……"） |

删除都是软删除，30 天后清理，期间可以撤销。

### 8.2 时间与时区

online-report 只服务国内工厂，全部按北京时间存。DayMate 面向公众，用户可能在海外，所以做法不同：

- 带时间的日程用 `timestamptz` 存（数据库里统一是 UTC），全天日程用 `date` 存。
- 每个用户有时区设置（默认 `Asia/Shanghai`），显示、AI 解析、提醒计算都按用户时区。
- 接口返回带时区偏移的 ISO 时间。

### 8.3 重复日程

- 用 RRULE 字符串存。这是日历行业的标准格式，以后导入导出 ICS 不用转换。
- 带时间的重复日程按日程自己的时区（创建时用户的时区）展开墙上时间，所以跨夏令时也保持"每周一 9 点"；全天日程是浮动日期，与时区无关。
- 没有这一天的月份跳过（每月 31 日、每年 2 月 29 日），与 RFC 5545 一致。
- P1 支持每天、工作日、每周（可选星期几）、每月、每年，可以设结束日期或次数。
- 查询某段时间时，按用户时区展开成具体场次，不预先生成所有场次。
- 不支持只改其中一次（P2 做）。

### 8.4 冲突检测

保存前检查同一用户在同一时间段是否已有日程（包括重复日程展开后的场次），有冲突就在卡片上提示，比如"和 15:00 的周会冲突"，由用户决定。纯规则判断，不调 AI。

## 9. 提醒与推送

### 9.1 统一出口

借鉴 online-report 的 `server/src/notify.js`：所有主动推送都只调用 `notify()`，不在各处自己发。

```
notify({ userId, kind, title, body, link })
  1. 写一条站内消息（notifications 表），用户打开应用就能看到
  2. 按用户设置和免打扰时段，发往各个渠道：Web Push、邮件
  3. 每个渠道的发送结果记入 notification_deliveries
```

`kind` 有四种：`reminder`（日程提醒）、`brief`（早报、复盘）、`suggestion`（AI 建议）、`system`（系统通知）。以后接 App 推送、小程序订阅消息，只需加一个渠道发送器。

### 9.2 各渠道的实际情况

| 渠道 | 能否收到 | 说明 |
|---|---|---|
| 站内消息 | 都能 | 打开应用时看到；应用开着时到点弹出页内提醒 |
| Web Push：iPhone | iOS 16.4 及以上，并且已"添加到主屏幕" | 走苹果推送服务，国内可用 |
| Web Push：电脑上的 Edge、Firefox、Safari | 一般可以 | 各自用自己的推送服务，以实测为准 |
| Web Push：Chrome（安卓和电脑） | 国内基本收不到 | 依赖 Google 推送服务 |
| Web Push：国产手机浏览器、微信内置浏览器 | 基本不支持 | |
| 邮件 | 能 | 要求邮箱已验证；适合提前较久的提醒和早报 |
| App 推送、小程序订阅消息 | P3 | 真正可靠的到点提醒要靠这两个渠道 |

结论：H5 阶段到点提醒的到达率有天然上限。M4 开发时在本机自动化测试用的 Chrome 里订阅推送直接失败（这类浏览器不带推送服务），所以真实设备上的 Web Push 到达情况要上线到正式域名后用真机验证（iPhone 添加到主屏幕、电脑 Edge / Safari）。"我的 → 通知设置"要告诉用户当前设备能用哪些方式，并引导 iPhone 用户把网页添加到主屏幕。

### 9.3 提醒调度

- 保存日程或待办时，按提醒设置写入 `reminders` 表（触发时间、状态）；日程修改或删除时同步更新。重复日程只写下一场，这一场发完再写下一场。
- 后台每 30 秒扫描一次到期提醒，用 `FOR UPDATE SKIP LOCKED` 取出并标记，保证不重复发；失败最多重试 3 次。
- 服务重启期间错过的提醒：超时 30 分钟以内的照常发送；更早的不再推送，只在站内消息里标成"错过的提醒"。
- 早报、复盘：每分钟检查哪些用户到了设定时间、今天还没生成，限制并发后逐个生成并推送。

### 9.4 用户设置

- 每类消息可以分别开关各个渠道。
- 免打扰时段（默认 23:00–7:00）只拦 AI 建议类消息，用户自己设的日程提醒照常发送。
- 早报、复盘的时间可以改，也可以关掉。

## 10. 个性化与主题

### 10.1 主题 token（沿用 online-report）

- 组件里只用语义色（背景、卡片、主色、强调色、成功/警告/危险等），不写死颜色值；换主题只换一组 CSS 变量。参考 online-report 的 `frontend/src/theme/themes.css`。
- 除了颜色，圆角、阴影、字体、间距密度、卡片质感也做成 token，让主题之间不只是颜色不同，整体气质也不同。
- 沿用 online-report 的颜色检查脚本 `frontend/scripts/check-theme-colors.mjs`，提交前必须通过。

### 10.2 预设主题

M0 已做 12 套，分两组（id 和名称在 `packages/shared/src/theme.ts`，token 在 `apps/web/src/theme/themes.css`）：

- **经典**：暖纸手账、极简黑白、夜航、水墨
- **个性**：像素游戏、赛博霓虹、复古终端、千禧糖果、孟菲斯、蒸汽波、号外报纸、工程蓝图

主题之间不只换颜色，纹理背景、卡片边框（粗细、虚线、双线）、阴影（错位硬阴影、霓虹发光）、标题字体（衬线、楷体、等宽）和文字发光也都是 token。`themes.test.ts` 按 WCAG 公式检查每套主题的文字对比度，新增主题必须通过。

### 10.3 DIY

| 可调项 | 说明 |
|---|---|
| 主色 | 用取色器选一个颜色，自动生成整套配色（在 OKLCH 色彩空间里用 culori 计算），并检查文字对比度是否达到 WCAG AA |
| 背景 | 纯色、渐变，或者自己上传图片；可调模糊和遮罩，保证文字看得清 |
| 字体 | 系统黑体、宋体、圆体、手写体。中文字体文件很大，只用系统字体或按需加载精简子集 |
| 圆角、卡片质感 | 方角或圆角；平面、阴影或毛玻璃 |
| 日历与首页 | 每周从周一还是周日开始；首页模块的顺序和显隐 |
| 深浅色 | 跟随系统 / 固定浅色 / 固定深色 |

### 10.4 实现要点

- 主题设置存在 `user_settings.theme_json`，跨设备同步。
- 本机也缓存一份。页面加载时，在 React 启动前用一小段内联脚本先套上主题，避免先白一下再变色。
- 上传的背景图先在浏览器里压缩成 WebP（最长边 1920 像素、不超过 1MB）再上传，存在服务器的数据卷里。
- P2：主题可以导出成分享码，别人粘贴就能套用。

## 11. 数据模型（P1）

所有业务表都带 `user_id`，查询一律按当前用户过滤，在数据访问层统一处理。主键用 UUID v7（按时间递增，利于索引；放在链接里也无法按顺序遍历）。

| 表 | 用途 | 主要字段 |
|---|---|---|
| `users` | 账号 | 用户名、邮箱、邮箱验证时间、密码哈希、昵称、头像、时区、状态、连续登录失败次数、锁定截止时间 |
| `user_sessions` | 登录会话（一台设备一行） | 刷新令牌哈希、设备信息、IP、过期时间、最近使用时间、作废时间 |
| `email_tokens` | 邮箱验证 / 重置密码 | 用途、令牌哈希、过期时间、使用时间 |
| `user_settings` | 偏好设置 | 主题、每周起始日、默认时长、默认提醒、早报和复盘时间、免打扰时段、各渠道开关、是否说完直接保存 |
| `calendars` | 日历本 | 所有者、名称、颜色、是否默认 |
| `events` | 日程 | 日历本、标题、备注、地点、参与人、是否全天、开始和结束时间（或日期）、重复规则、时区、提醒设置、来源（语音/文字/手动）、语音记录 ID |
| `tasks` | 待办 | 标题、备注、截止日期或时间、优先级、状态、完成时间、来源 |
| `entries` | 记录 | 日期、发生时间、内容、标签、心情、关联日程、来源 |
| `reminders` | 待发送的提醒 | 对象（日程/待办）、对应场次、触发时间、状态、尝试次数 |
| `daily_briefs` | 早报、复盘 | 日期、类型、正文、建议、所用模型 |
| `notifications` | 站内消息 | 类型、标题、正文、跳转链接、已读时间 |
| `notification_deliveries` | 各渠道发送结果 | 消息、渠道、状态、错误、发送时间 |
| `push_subscriptions` | Web Push 订阅 | endpoint、密钥、设备信息、连续失败次数 |
| `voice_logs` | 语音识别记录（不存音频） | 识别文字、最终文字、时长 |
| `ai_calls` | AI 调用记录 | 用途、模型、token 数、耗时、是否成功 |
| `usage_daily` | 每日额度计数 | 日期、语音次数、AI 次数 |
| `uploads` | 上传的文件（主题背景等） | 路径、类型、大小 |

数据保留期：`voice_logs` 90 天；软删除的数据 30 天；`ai_calls` 180 天。到期由后台任务清理。

## 12. 接口清单（P1）

统一前缀 `/api`。错误格式沿用 online-report：`{ error, code, detail? }`。

后端不带 `/api` 的地址一律当作页面处理（内部改写到 `/__web`），所以页面地址可以和接口同名（如页面 `/me` 和接口 `GET /api/me`），互不影响。

| 模块 | 接口 |
|---|---|
| 账号 | `POST /auth/register`、`POST /auth/login`、`POST /auth/refresh`、`POST /auth/logout`、`POST /auth/verify-email`、`POST /auth/resend-verification`、`POST /auth/forgot-password`、`POST /auth/reset-password` |
| 我的 | `GET /me`、`PATCH /me`、`PUT /me/password`、`DELETE /me`（注销）、`GET /me/sessions`、`DELETE /me/sessions/:id`、`GET /me/settings`、`PUT /me/settings` |
| 语音 | `POST /speech/recognize` |
| AI 助手 | `POST /assistant/parse`（解析但不保存；如果是提问，直接返回回答）、`POST /assistant/commit`（保存确认后的卡片，全部成功或全部不保存，并记下最终文字） |
| 日历本 | `GET /calendars`、`POST /calendars`、`PATCH /calendars/:id`、`DELETE /calendars/:id` |
| 日程 | `GET /events?from=&to=`（返回展开后的重复场次）、`POST /events`、`GET /events/:id`、`PUT /events/:id`（整体替换，重复日程改整个系列）、`DELETE /events/:id`、`POST /events/:id/restore` |
| 待办 | `GET /tasks?status=open\|done\|all`、`POST /tasks`、`PATCH /tasks/:id`（含 `done` 勾选）、`DELETE /tasks/:id`、`POST /tasks/:id/restore` |
| 记录 | `GET /entries?date=` 或 `?from=&to=`、`POST /entries`、`PATCH /entries/:id`、`DELETE /entries/:id`、`POST /entries/:id/restore`（正文里的 #标签 自动提取） |
| 首页 | `GET /today`（今天的日程、待办、记录、早报、复盘一次返回） |
| 搜索 | `GET /search?q=`（按关键词搜日程、待办、记录） |
| 消息 | `GET /notifications`、`GET /notifications/unread-count`、`POST /notifications/:id/read`、`POST /notifications/read-all` |
| 推送 | `GET /push/config`、`POST /push/subscriptions`、`DELETE /push/subscriptions`、`POST /push/test`（发一条测试通知） |
| 早报复盘 | `POST /briefs/generate`（手动生成，不推送；今天页 `GET /today` 里带 `briefs`） |
| 上传 | `POST /uploads/background` |
| 运维 | `GET /health` |

## 14. 安全与隐私

- 全站 HTTPS；加安全响应头（@fastify/helmet）；跨域只允许本站来源（以后加上 App 的来源）。
- 所有接口都做输入校验。所有查询都按当前用户过滤，权限在后端校验，不靠前端隐藏。
- 登录、注册、语音、AI 接口单独限流，另外有每日额度。
- 密钥只放 `.env`，仓库里只提交 `.env.example`。
- 应用日志不打印密码、令牌，也不打印用户说的原话。
- 个人信息保护：
  - 注册时勾选同意《用户协议》和《隐私政策》。
  - 隐私政策列出用到的第三方服务（百度语音识别、大模型厂商、邮件服务）以及传给它们的数据。
  - 提供注销账号：申请后 7 天内可撤销，到期彻底删除所有数据。
  - P2 提供数据自助导出。

| 变量 | 说明 |
|---|---|
| `APP_DOMAIN`、`PUBLIC_BASE_URL` | 域名；邮件和推送里的链接 |
| `POSTGRES_PASSWORD`、`DATABASE_URL` | 数据库 |
| `JWT_SECRET` | 访问令牌的签名密钥 |
| `BAIDU_ASR_API_KEY`、`BAIDU_ASR_SECRET_KEY`、`BAIDU_ASR_MODE` | 百度语音识别（同 online-report） |
| `AI_BASE_URL`、`AI_API_KEY`、`AI_MODEL_PARSE`、`AI_MODEL_SUMMARY` | 大模型 |
| `SMTP_HOST`、`SMTP_PORT`、`SMTP_USER`、`SMTP_PASS`、`MAIL_FROM` | 邮件 |
| `VAPID_PUBLIC_KEY`、`VAPID_PRIVATE_KEY`、`VAPID_SUBJECT` | Web Push |
| `QUOTA_ASR_PER_DAY`、`QUOTA_AI_PER_DAY` | 每人每日额度 |

### 15.3 国内部署注意

- 国内服务器上的域名要先完成 ICP 备案，否则 80/443 端口无法访问，也就申请不了证书、用不了麦克风。想先试运行可以用香港服务器（不需要备案）。
- 国内服务器直接拉 Docker Hub 镜像经常失败：配置云厂商的镜像加速，或者把镜像推到阿里云、腾讯云的容器镜像服务。构建时 npm 换国内源。
- 起步阶段 2 核 4G 的服务器就够用（数据库和应用放在同一台）。

## 16. 测试与质量

- **单元测试**（Vitest）：日期解析、时区换算、重复展开、提醒时间计算、主题色板生成、AI 输出校验、移植过来的录音工具函数。

- **AI 评测集**：见 7.6。
- **端到端测试**（Playwright）：注册 → 登录 → 文字输入一句话 → 确认卡片 → 日历上出现 → 到点收到站内提醒。语音部分用模拟的识别结果代替。
- **真机清单**：iPhone Safari（含添加到主屏幕后的推送）、安卓 Chrome、安卓国产浏览器、微信内置浏览器、电脑 Chrome 和 Edge，逐项检查录音、识别、推送、主题。

## 18. 待确认事项与风险

**需要你决定或准备的：**

1. **域名和服务器**：国内服务器需要 ICP 备案，一般要一到几周，建议尽早开始。
2. **大模型厂商**：DeepSeek、通义千问等选一家开通账号。开发期可以先用 online-report 现有的配置。
3. **邮件服务**：阿里云邮件推送或腾讯云 SES，需要在域名上配置 SPF/DKIM。
4. **视觉方向**：M0 出样张后选。
5. **中文名和图标**：PWA 添加到主屏幕时会显示。

**主要风险：**

| 风险 | 应对 |
|---|---|
| H5 推送到达率低 | 站内消息兜底 + 邮件；引导 iPhone 用户添加到主屏幕；P3 的 App 和小程序彻底解决 |
| AI 把时间解析错 | 确认卡片 + 评测集 + 14 天日期对照表 |
| 人名、地名识别不准 | 卡片可以改；用纠错样本做自训练 |
| 语音和 AI 调用成本 | 每日额度、限流；不活跃用户不生成早报和复盘 |
| 合规（备案、隐私） | 见 7.5、14、15.3；上线前逐项核对 |
